# Keeping guests apart

A VM is only worth having if what's in it stays in it, so here's where that stands.

What's in place for Windows guests:

- **Programs in a VM are kept apart on the GPU, with the gaps listed below.** Each process gets its own GPU page tables, like on real Windows. My test has one process hold a secret and another try to read and overwrite it by its GPU address. On the Rust backend it read none of the 16,384 words, in every try, and its writes left the secret whole. The same read got all 16,384 words of a process's own secret, and of one it was properly given through a shared handle, and the same write overwrote a process's own buffer, so the test does reach memory when it's allowed to. The one thing they still share is a block of fences, which only holds counters. On an AMD card each process gets its own GPU address space too, but I haven't run that test there yet. What that test doesn't cover: a tiled copy is checked against its surface by the pitch of its rows, and the copy runs by the width, so a width over the pitch isn't caught. Handle numbers start again from the first after about 50 million are made, and a new one can land on one still in use. On AMD, memory a program frees can go back to the guest while work on it is still running, after a queue has failed.
- **Windows never talks to the host's driver.** It talks to my daemon, and the daemon makes the calls. Sizes and ranges in every message get checked. The message parsers and the core's handlers are fuzz tested. The AMD backend's private-data parsers have unit tests and no fuzz test yet.
- **You can cap a VM's video memory.** With a limit set, a program that goes over it when it makes a buffer loses its device. A buffer that a program maps past its size is made larger without that check, and counts from the next buffer on. Without one, the VM is told to leave a share of the card for the host, but that's a budget and not a wall. A second GPU VM won't start until the first one has a cap.
- **QEMU and the daemon are jailed.** Each one is given what that VM needs: its disk, its firmware variables, its memory, its run folder and its shared folder, and for the daemon the cards. Not the rest of your home folder and not another VM. A disk's header can name backing files, and QEMU's jail is given read access to each one at the start. The NVIDIA daemon's jail holds the device files of every NVIDIA card on the PC and every render node, not only the VM's own card. The daemon has no network at all. Neither can gain privileges, even through a setuid program, or trace your other programs. It's Landlock and seccomp, which need no root, and where bubblewrap can make namespaces, QEMU gets those too. Landlock holds back TCP, and not UDP or SCTP, and its limits on abstract sockets and signals need a kernel from 6.12. Namespaces don't include a network of their own, and the machine's row doesn't say when Landlock lacks one of these. That's every network mode: passt and a bridge's helper start just before QEMU's jail goes on and hand it what it needs, and a USB device you pass to a VM is handed to QEMU open. Turn a machine's sound off in its settings, or have no PipeWire running, and QEMU gets the sockets it needs handed to it and can't open any more, so it can't reach your desktop's either. A PC that can't do the Landlock part won't start a GPU machine unless you allow that machine in its settings, and then its row says it isn't jailed. If you start QEMU yourself, as [standalone](standalone.md) describes, the daemon is still jailed, and QEMU's jail is yours to do.
- **Dragged files take a path of their own.** Unless you turn Drag Files off in the machine's settings, while a viewer is open a small helper runs in the Windows user's session and listens on one more port, which QEMU forwards from loopback like the agent's and Windows' firewall opens to this PC's end of the private link only. It needs the machine's token. Files you drop go into a folder of that user's in the guest. Files you drag out are written under `~/.cache/guesthouse/dragged`, and the guest gets no say in where: a name that would lead out of that folder is refused. The guest can only offer files while you drag out of its screen with the button down. They are copied to that folder as you carry them, as large as the guest makes them, and removed again if you drop them on nothing. What you did drop somewhere stays there until that machine's screen is next opened. No folder is shared for this, so the jail stays as it is but for that port.
- **Remote Desktop and SSH only answer port forwards.** A new Windows machine has Remote Desktop on, and SSH if you choose it. Windows' firewall lets either in only from this PC's end of the private link, where QEMU's port forwards arrive, so even on a bridged network they aren't on your LAN. A forward listens on loopback, so other users on this PC can reach it, and they still need the account's password, or one of your keys for SSH. That's how it is on a Linux host. On a Windows host a guest has Remote Desktop on for any address its network gives it, and a port forward answers this PC's own subnet on every network profile, as [Windows host](windows-host.md) says.
- **Defender is as Windows sets it, unless you say otherwise.** Guesthouse never switches off or weakens Defender, the firewall, SmartScreen, Windows Update, UAC, Secure Boot, the TPM or BitLocker by itself, and [lean Windows](recipes.md#lean-windows) doesn't either. The firewall only gains the rules that let the agent, Remote Desktop and SSH in from this PC. The one exception is a question of its own, off unless you turn it on: leaving the folders a recipe names out of Defender's real-time scanning, for games or builds you trust. The machine's settings and `guesthouse-vm show` say when a machine does that, and can take it back. [Recipes](recipes.md#leaving-folders-out-of-virus-scanning) has the details.
- **A machine can be held to your VPN.** Pick an interface under Only through in a NAT machine's network settings, such as `wg0`, and everything the guest sends goes out through it and nowhere else, IPv4, IPv6 and DNS. passt does the binding, so it needs passt 2025_04_15 or newer, and the machine won't start without it, or with the interface missing, rather than fall back to QEMU's own network. DNS goes to the interface's own server, from systemd-resolved or NetworkManager, unless you type one. When the interface has an IPv6 address, the guest is also given the IPv6 servers and search domains in this PC's `/etc/resolv.conf`, and asks those too. passt alone lets new TCP connections out the normal way once a VPN deletes its interface, as `wg-quick down` and most clients do on disconnect, so a small guard beside passt refuses every connection from the moment the interface goes. The machine's network then stays cut, even after the VPN is back, until you start it again, and its settings page says so. I've tested it with Tailscale on this PC and with a tunnel in a test namespace, with a Windows guest. Not on SELinux or AppArmor yet. Ubuntu machines can't have it, as their network is fixed.
- **The guest agent has a token per machine.** The guest agent's port is on loopback with a token per machine, which the app sends as the first line of each connection. Other users on the PC can reach the port.
- **A failing program only costs itself.** A program that keeps failing on the GPU loses its own device, and the rest of the VM carries on.

What a guest can still do:

- **Get in the way.** A program can't read or change its neighbours, but trying faults the GPU, and in the one try I timed, that froze other work on the card for about four seconds, the host's included. If too many programs fault in a minute, that VM's GPU stops until Windows restarts, and the app says so. That count is of programs whose queues fail. A fault on the copy that brings a frame to the screen isn't in it, and on AMD neither is a hang that amdgpu ends with a reset.
- **See some of your hardware.** Windows sees your card's real UUID and ECID, your CPU and how much RAM you have.
- **Reach the card's driver.** The daemon keeps the card open, so a bug in it that hands a guest the daemon also hands it the host's GPU driver, NVIDIA's, amdgpu or xe, and a bug there is a bug in your kernel. On Intel the daemon runs the guest's work on the card through xe by default. Only run a Windows guest you'd trust with that.
- **Reach your audio server.** With sound, QEMU keeps its connection to PipeWire, so a QEMU taken over could in principle record from your microphone, not just play. On Ubuntu 24.04, whose Landlock can't hold back sockets and which doesn't let bubblewrap make namespaces out of the box, it could also reach your desktop's other sockets, like the session bus. The machine's row says when that's the case. Turning the machine's sound off closes both. A Linux guest has no sound, so its QEMU never has either.
- **Reach your loopback services on the default network.** A new machine's NAT is QEMU's own, with passt off, and on it the guest reaches whatever listens on this PC's loopback through 10.0.2.2. That's your own local services, and the port forwards of your other machines. Ubuntu machines always have this network. To avoid it, turn passt on in the machine's network settings, which maps no host loopback, or set the network to none.
- **Do anything to a drive you give it.** A drive of this PC that you give a VM is the guest's, all of it. It can read, change or wipe every byte, so a drive with your own files on it is a drive with your files at its mercy. QEMU gets the drive open and nothing else of your devices, and this PC can't mount it while the VM runs. And if you give yourself access to a drive with the rule the settings show, every program of yours can write to it, not only the VM.

What's still coming:

- **Jails for the rest.** The virtual TPM, machines with no GPU and installs run without the jail.
- **Trust a Linux guest like you trust yourself.** A Linux guest gets the GPU the way a program of yours does. It can do what your user can do to the card, it sees whole-card sensor and memory readings, and it can slow or crash your GPU session, which takes your desktop with it. It only gets calls on the list, it can only name its own GPU clients, the device's limits on video memory, system memory and objects don't hold against every call a guest can make, and QEMU is in the same jail as a Windows guest's, plus the chosen card's device files, as that's how the GPU gets to the guest. As far as I could test, it can't reach QEMU's memory or anyone else's GPU work. A bug in this device only gets a guest QEMU's jail, but a bug in NVIDIA's driver is a bug in your kernel. Treat a guest as being as trusted as you, and don't run one you don't trust.
