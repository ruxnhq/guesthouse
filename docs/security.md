# Keeping guests apart

A VM is only worth having if what's in it stays in it, so here's where that stands.

What's in place for Windows guests:

- **Programs in a VM can't see each other on the GPU.** Each process gets its own GPU page tables, like on real Windows. My test has one process hold a secret and another try to read and overwrite it by its GPU address. On the Rust backend it read none of the 16,384 words, in every try, and its writes left the secret whole. The same read got all 16,384 words of a process's own secret, and of one it was properly given through a shared handle, and the same write overwrote a process's own buffer, so the test does reach memory when it's allowed to. They share one block of fences, which only holds counters. On an AMD card each process gets its own GPU address space too.
- **Windows never talks to the host's driver.** It talks to my daemon, and the daemon makes the calls. Sizes and ranges in every message get checked, the parsers and handlers are fuzz tested, and what a guest holds, such as its processes, address spaces, queues and sync objects, stops at a limit.
- **You can cap a VM's video memory.** With a limit set, an allocation that would take the VM past it is refused, and that holds for growing one when it's first mapped too. Without one, the VM is told to leave a share of the card for the host, but that's a budget and not a wall. A second GPU VM won't start until the first one has a cap.
- **QEMU, the virtual TPM and the daemon are jailed.** That's every machine, with a GPU or without, and an install too. The files each one may open are that VM's own: its disk, its firmware variables, its memory, its run folder and its shared folder, for the TPM its own folder, and for the daemon its card. The daemon has no network at all. Neither can gain privileges, even through a setuid program, or trace your other programs. It's Landlock and seccomp, which need no root, and where bubblewrap can make namespaces, QEMU gets those too. That's every network mode: passt and a bridge's helper start just before QEMU's jail goes on and hand it what it needs, and a USB device you pass to a VM is handed to QEMU open. Turn a machine's sound off in its settings, or have no PipeWire running, and QEMU gets the sockets it needs handed to it and can't open any more, so it can't reach your desktop's either. QEMU changes a file only through one it has open, makes no socket but TCP, UDP, netlink and, with sound, unix ones, and has no System V shared memory. A PC that can't do the Landlock part starts a machine only when you turn on Start without a jail in that machine's settings, and then its row says it isn't jailed. Where the kernel's Landlock can't hold back something the machine's jail would, such as UDP ports on a bridged machine, the row names it. If you start QEMU yourself, as [standalone](standalone.md) describes, the daemon is still jailed, and QEMU's jail is yours to do.
- **Dragged files take a path of their own.** Unless you turn Drag Files off in the machine's settings, while a viewer is open a small helper runs in the Windows user's session and listens on one more port, which QEMU forwards from loopback like the agent's and Windows' firewall opens to this PC's end of the private link only. It needs the machine's token. Files you drop go into a folder of that user's in the guest. Files you drag out are written under `~/.cache/guesthouse/dragged`, and the guest gets no say in where: a name that would lead out of that folder is refused. The guest can only offer files while you drag out of its screen with the button down. They are copied to that folder as you carry them, as large as the guest makes them, and removed again if you drop them on nothing. What you did drop somewhere stays there until that machine's screen is next opened. No folder is shared for this, so the jail stays as it is but for that port.
- **On a Linux PC, Remote Desktop and SSH only answer port forwards.** A new Windows machine has Remote Desktop on, and SSH if you choose it. Windows' firewall lets either in only from this PC's end of the private link, where QEMU's port forwards arrive, so even on a bridged network they aren't on your LAN. A forward listens on loopback, so other users on this PC can reach it, and they still need the account's password, or one of your keys for SSH. On a Windows host the guest's Remote Desktop answers this PC's addresses, and a bridged guest's answers the network it's on too. An Ubuntu guest there takes SSH passwords from the loopback and this PC, and when bridged from its own network too, and keys from anywhere. [The Windows host](windows-host.md) has the details.
- **Defender is as Windows sets it, unless you say otherwise.** Guesthouse never switches off or weakens Defender, the firewall, SmartScreen, Windows Update, UAC, Secure Boot, the TPM or BitLocker by itself, and [lean Windows](recipes.md#lean-windows) doesn't either. The firewall only gains the rules that let the agent, Remote Desktop and SSH in from this PC. The one exception is a question of its own, off unless you turn it on: leaving the folders a recipe names out of Defender's real-time scanning, for games or builds you trust. The machine's settings and `guesthouse-vm show` say when a machine does that, and can take it back. [Recipes](recipes.md#leaving-folders-out-of-virus-scanning) has the details.
- **A machine can be held to your VPN.** Pick an interface under Only through in a NAT machine's network settings, such as `wg0`, and everything the guest sends goes out through it and nowhere else, IPv4, IPv6 and DNS. passt does the binding, so it needs passt 2025_04_15 or newer, and the machine won't start without it, or with the interface missing, rather than fall back to QEMU's own network. DNS goes to the interface's own server, from systemd-resolved or NetworkManager, unless you type one, and the guest is told none of this PC's DNS servers or search domains. passt alone lets new TCP connections out the normal way once a VPN deletes its interface, as `wg-quick down` and most clients do on disconnect, so a small guard beside passt refuses every connection from the moment the interface goes. The machine's network then stays cut, even after the VPN is back, until you start it again, and its settings page says so. I've tested it with Tailscale on this PC and with a tunnel in a test namespace, with a Windows guest. Ubuntu machines can't have it, as their network is fixed.
- **A guest can't reach this PC's loopback.** On QEMU's own network, which a machine has unless passt is on and an Ubuntu machine always has, 10.0.2.2 is where this PC's forwards to the guest come from. It leads the guest to none of the services on this PC's loopback, yours or another machine's forwards, and neither does the IPv6 prefix. The guest's packets to a loopback address are dropped. passt does the same, with its loopback mapping off. The internet, DNS and the shared folder work as usual. It's a setting of the QEMU that comes with Guesthouse ([the patch](../qemu/qemu-host-loopback.patch)). At each start the app asks the machine's QEMU whether it knows the setting, and doesn't start one that doesn't.
- **A shared folder answers only its own address.** On a Linux PC the folder is served at `http://10.0.2.4/KEY/`, with a key the machine keeps in its folder, and every other address gets nothing. A Windows guest is given the address at each start, and the drive belongs to the user's own logon. For a macOS or other guest the settings page and `guesthouse-vm show` give it. Turn on Read Only beside the folder and the guest can open its files and can't change, add or remove anything. Only regular files and folders are opened, a link the guest copies or moves has to still lead inside the folder, and a connection that says nothing for a minute ends.
- **The daemon's sockets are for its owner alone.** The guest agent's port is on loopback with a token per machine. QEMU picks that port, and the helpers', when it starts, and tells the app which on its monitor in the run folder. The app only sends the token, to the agent or to a helper, on a connection that the machine's own QEMU has taken, and asks nothing while that QEMU isn't running.
- **A machine on a Windows host belongs to the user who made it.** The service keeps that user's account in the machine's settings. Only that user, the system and elevated administrators see the machine, its log, its account and its viewer's key, or act on it. To anyone else it isn't there. Its disk is reached only through handles that follow no links, and `C:\Guesthouse` in the guest, where the guest's SYSTEM runs its scripts from, can be changed only by SYSTEM and administrators. The serial port is read by a relay jailed in a less privileged AppContainer, and only from the machine's own worker.
- **A disk is started only on the files it's built on.** The machine's settings keep the backing files of its disk. A start compares them with the disk's header, and QEMU is given each disk as a node with those files as its backing nodes. Every CD drive is read as raw. A shared folder that holds a machine's disk, or a file one is built on, is refused.
- **A new device for remote view is named by its fingerprint.** Accepting or declining a device that wants to pair is `pair accept FINGERPRINT`, and the guest answers only the device with that fingerprint.
- **A machine with remote view on announces itself on the local network.** While it runs, its name and port, and its fingerprint, go out over mDNS on this PC's real networks, for remoteman's viewers to find. A machine with remote view off announces nothing.
- **Updates and downloads are checked.** The Windows app offers an update only from a `guesthouse-windows-latest.json` that a release key signed, and runs an installer only when its SHA-256 matches the one in that file. The Mac app fetches a guest driver package only from a manifest signed with the same key. `install.sh` checks each download against the SHA-256 it holds. The package repositories are signed, and [the install page](install.md#packages) gives the key's fingerprint to check before apt or dnf takes it. [RELEASING.md](../RELEASING.md) says how the key is used.
- **A failing program only costs itself.** A program that keeps failing on the GPU loses its own device, and the rest of the VM carries on.

What a guest can do:

- **Get in the way.** A program can't read or change its neighbours, but trying faults the GPU, and in the one try I timed, that froze other work on the card for about four seconds, the host's included. If five programs fault within a minute, that VM's GPU stops until Windows restarts, and the app says so. Work the host driver ends early counts as a fault too.
- **See some of your hardware.** Windows sees your card's real UUID and ECID, your CPU and how much RAM you have.
- **Reach the card's driver.** The daemon keeps the card open, so a bug in it that hands a guest the daemon also hands it the host's GPU driver, NVIDIA's, amdgpu or xe, and a bug there is a bug in your kernel. Only run a Windows guest you'd trust with that.
- **Reach your audio server.** With sound, QEMU keeps its connection to PipeWire, so a QEMU taken over could in principle record from your microphone, not just play. On Ubuntu 24.04, whose Landlock can't hold back sockets and which doesn't let bubblewrap make namespaces out of the box, it could also reach your desktop's other sockets, like the session bus. The machine's row says when that's the case. Turning the machine's sound off closes both. A Linux guest has no sound, so its QEMU never has either.
- **Do anything to a drive you give it.** A drive of this PC that you give a VM is the guest's, all of it. It can read, change or wipe every byte, so a drive with your own files on it is a drive with your files at its mercy. QEMU gets the drive open and nothing else of your devices, and this PC can't mount it while the VM runs. And if you give yourself access to a drive with the rule the settings show, every program of yours can write to it, not only the VM.

A Linux guest:

- **Trust a Linux guest like you trust yourself.** A Linux guest gets the GPU the way a program of yours does. It can do what your user can do to the card, it sees whole-card sensor and memory readings, and it can slow or crash your GPU session, which takes your desktop with it. It only gets calls on the list, it can only name its own GPU clients, and QEMU is in the same jail as a Windows guest's, plus the chosen card's device files, as that's how the GPU gets to the guest. As far as I could test, it can't reach QEMU's memory or anyone else's GPU work. A bug in this device only gets a guest QEMU's jail, but a bug in NVIDIA's driver is a bug in your kernel. Treat a guest as being as trusted as you, and don't run one you don't trust.
